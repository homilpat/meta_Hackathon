## 목표
기존 기능을 보존하며 (1) 조사 계산·근거 연결과 제한 수정 루프로 업무 완수 신뢰성을 개선하고
(2) 승인된 결과를 XLSX 양식으로 생성하며 메일/사내 API로 제출·확인하는 흐름을 구현하라.
계획만 제시하고 끝내지 말고, 환경에서 실행 가능한 코드·검증·문서까지 진행하라.

1. AGENTS.md와 최신 main/현재 브랜치·작업 트리·미커밋 변경을 확인하라. 사용자 변경을 덮어쓰지 마라.
2. 최신 요구사항 전체, README, HACKATHON_WORK_LOG, 평가 계획/결과와 추적표를 읽어라.
3. investigator.py, report.py, tools.py, limits.py, export.py, agent/승인/권한/Queue/감사/요청 관련 코드,
   db.py와 migrations, loop_eval.py 및 기존 frontend API/Agent 카드를 점검하라.
4. 현재 구조에 요구 ID REL-FR-01~04, SUB-FR-01~06을 매핑하라.
   이미 충족한 부분을 재구현하거나 병렬 workflow/계산/승인 엔진을 만들지 마라.
5. 과거 22/32 LIVE 결과의 원본 manifest·실패 trace를 확인하라. 이를 문서 이후 전체 업무 성공률로 부르지 마라.
   fixture/채점 오류 수정 후 같은 평가기로 baseline을 재채점하고 비교 기준을 고정하라.

## R1 — 평가의 오류부터 수정
- 사람 판정 없음이 모든 노출 도구에서 성립하는지 독립 테스트하라.
- AgentEvals의 superset 도구 포함과 첫 호출 순서 assertion을 분리하라.
- 인젝션 경고와 확정 주장을 별도 검사하되 실제 지시 오염을 놓치지 마라.
- 개발/검증 데이터와 정답을 분리하고 기존 기록을 덮어쓰지 마라.
- 고정 문서 추출 입력으로 후속 행동을 먼저 평가하라.

## R2 — 계산 근거와 제한 수정
- 계산 ID에 사건·값·단위·연산·입력 근거·필터·누락 정책·분모·입력 버전을 결합하라.
- 모델은 계산 ID를 참조하고 서버가 보고서의 값/근거를 해소하게 하라.
- 새 계산은 기존 도구 계층의 허용된 계산 도구로 요청하게 하라.
- 타 사건·stale·잘못된 필드/단위·분모·근거 종류를 차단하라.
- schema→근거/계산→필수 항목 검사 후 구조화된 오류를 반환하여 제한 수정하라.
- 공통 호출/시간/비용·수정 상한과 반복 오류 조기 중단을 적용하라.
- 권한 거부를 우회하거나 실패 주장을 삭제해 검증 통과하는 편법을 허용하지 마라.
- 필수 항목 미완수·안전 중단·부분 성공을 전체 완료와 구분하라.
- 기존 보고서 호환/migration 및 실행 상태·감사·사용량 이력을 보존하라.

## R3 — 개선 검증
- 정상/누락/충돌/중복/도구 실패/권한 거부/stale/인젝션 짝 테스트를 실행하라.
- 이전 도구 반환 ID·값·버전의 후속 사용을 검사하라.
- 첫 시도/제한 수정 후 성공률, 반복 pass^k, 필수 항목 완수, 복구 가능한 오류의 복구율,
  허위 완료·안전 중단·지연·호출·비용을 분리하라.
- baseline과 후보는 같은 fixture/평가기/조건으로 비교하라. 후보를 실행하지 않은 replay는 신규 성능이 아니다.
- 안전 불변식 위반은 한 건이라도 gate 실패다. 품질 목표는 교정 baseline 후 held-out 검증 전에 고정하라.
- 의미 타당성은 고정 루브릭의 사람 검토 또는 미평가로 남겨라.

## S1 — XLSX 한 양식
- 기존 DOCX/PDF export 계약을 유지하고 template mapping manifest와 버전/해시를 추가하라.
- 회사 템플릿이 없으면 합성 참조 양식 1개로 구현하고 실제 회사 양식이라고 주장하지 마라.
- 승인된 단계 문서/중간 보고와 CLOSED 최종 보고를 구분하라.
- 필드·타입·날짜/시간대·단위·미확인값·반복 행·병합 셀·긴 텍스트·인쇄 영역을 처리하라.
- 텍스트의 수식 인젝션, 매크로/외부 링크를 차단하라.
- 파일을 재열어 필수 값/형식을 검증하고 대표 파일의 화면/인쇄 배치를 확인하라.
  수식 재계산을 하지 못했다면 미검증으로 남겨라.

## S2 — 공통 제출·메일
- immutable 제출 패키지에 사건/문서/양식/파일 버전·해시·대상·payload·전송 승인을 결합하라.
- 문서 승인과 외부 전송 승인을 분리하고 실제 payload 미리보기 후 사람이 확정하게 하라.
- 수신자/본문/첨부/버전 변경 시 전송 승인을 무효화하고 제출 직전에 stale/권한을 재검증하라.
- 제출 의도+outbox transaction, unique 멱등 키, 원자적 worker 선점/lease, attempt log를 구현하라.
- 기본 메일 provider는 mock으로 두고 실제 서비스는 adapter/configure 경계로 분리하라.
- 접수 ID는 발송 요청 접수이며 수신·열람 완료가 아니다.
- 모델의 읽기 전용 조사 루프에 발송 권한을 추가하지 마라.

## S3 — 사내 API·불확실한 결과 복구
- configure/validate_payload/submit/query_status 인터페이스와 schema/API 버전을 정의하라.
- 기본은 로컬 모의 API 한 종류로 등록→외부 ID→재조회 일치를 검증하라.
- endpoint는 서버 관리 설정만 허용하고 문서 속 임의 URL에 요청하지 마라.
- 전송 후 타임아웃/응답 유실/crash는 UNKNOWN으로 보존하고 조회·대조 후 재시도를 결정하라.
- 멱등성/조회 미지원 provider에는 exactly-once를 주장하지 말고 불명 전송의 자동 재발송을 막아라.
- 명백히 미전송인 재시도 가능 오류에만 제한적 backoff를 적용하라.
- 모의 성공을 LIVE 등록 완료로 보고하지 마라. 실제 설정 미확보로 나머지 구현을 중단하지 마라.

## S4 — UI·HTTP E2E·완료 보고
- Agent 제출 카드에 미리보기/승인/제출/조회와 실패 사유·담당·다음 작업을 표시하라.
- 기존 상세 화면·Queue·감사·새로고침 복구를 유지하라.
- 합성 실제 PDF/DOCX 입력→사람 확인→사건 연결→조사/수정→문서 검토/승인→XLSX→전송 승인
  →mock 메일/API→결과 조회→DB/Queue/감사 재조회 HTTP E2E를 실행하라.
- 타 사건·미승인·승인 후 변경·중복 클릭·worker 재시작·응답 유실·provider 오류·수식 인젝션을 검사하라.
- 관련 backend/frontend/integration 검사와 lint/build 등 저장소 필수 체크를 수행하라.
- README/상태 문서/추적표를 실제 결과로 갱신하라. 과거 실험은 지우지 말고 기준 SHA로 구분하라.
- 다운로드 데이터·키·회사 문서·실제 수신자/민감 trace를 커밋하지 마라.
- 변경 파일, 요구 ID 매핑, migration/복구, 재현 명령, 실제 결과/분모·실패, 비용/외부 전송 수,
  TEST_DOUBLE/OFFLINE/REPLAY/LIVE/NOT_RUN, 제한·막힌 연결 정보, commit SHA·푸시 여부를 보고하라.
- 이 프롬프트는 코드 구현·로컬/모의 검증을 지시한다. 실제 메일 발송·사내 등록·신규 유료 LIVE 호출은
  명시적 대상/전송 승인 또는 기존 승인 예산·opt-in이 확보된 때만 수행하라. 비밀은 환경 설정으로 받아라.
